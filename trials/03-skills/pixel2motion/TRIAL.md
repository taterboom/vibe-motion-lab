# 03 技能 pixel2motion

日期：2026-11-13
版本：vibe-motion/skills f558ec4，技能装在 `.claude/skills/pixel2motion/`（v2）。Python 3.12（uv venv，在本目录 `.venv`）：Pillow 13.0、numpy 2.5、Playwright 1.65.1（Chromium 158 headless shell，装在用户缓存）。

## 做了什么

这是 2A 宣传片的预演，素材只用本目录的拷贝，没往 `../hiraishin` 写东西。

1. 输入：`../inputs/hiraishin-mark.svg`。技能要栅格图，所以用 Chromium 栅格化成 1024px：`input/source.png`（白底）和 `input/source_alpha.png`（透明）；原 SVG 拷贝在 `input/`。
2. 按 SKILL.md 三个阶段原样走：
   - 第 1 阶段：写动效简报（性格三词、用途、编排草图），见 `motion_spec.md`。
   - 第 2 阶段：`raster_logo_trace.py` 先描一遍当测量参考 → 自己写测量和拟合脚本（`outputs/fit_work/`）按复杂度阶梯拟合 → 每轮 `render_overlay.py` 出叠图和 IoU → `svg_path_audit.py` → `overlay_progress_strip.py`。
   - 第 3 阶段：手写 `motion.css` → `svg_to_js_html.py`（静态检查）→ `animate_svg_showcase.py` 出 `logo_motion.html` → `capture_motion_frames.py`（抽帧 + 最终帧比对）→ `probe_motion_continuity.py --probe`（缓动探针）→ `--ink-sweep`（连续性扫描）→ 同管线最终帧检查。
   - 预览：SKILL.md 里没有出视频/GIF 的脚本（README 提到了），自己用 `?t=` 逐帧 30fps 截图 + ffmpeg 出 `outputs/preview/preview.mp4` 和 `.gif`。
3. 动效一共改了 4 版（v1→v4），前三版的抽帧留在 `outputs/motion_v1..v3/`。

没有用自然语言「触发」技能：本次是子代理照 SKILL.md 手动走流程。

## 跑通了吗

改了才通。技能脚本本身没改，碰到的问题：

1. **描摹脚本在白底源图上直接报错**「No vector paths produced」。它取图像四边像素的中位数当背景色；这个标志是满版瓦片，四边大多是深绿，于是把深绿当成背景，阈值又被四角的白拉得很高，什么都没剩。换成透明版源图（走 alpha 模式）才出结果。满版 app 图标都会撞上这个问题。
2. **描摹结果把绿色阴影并进了黄色**（默认 6 色量化），IoU 却有 0.9979。技能的 IoU 只看「非白」轮廓，颜色错了看不出来。我另写了一个分颜色的 IoU（`outputs/fit_work/color_check.py`）补上。
3. **平滑度审计对锐角标志误报**：闪电本来就是尖角，`svg_path_audit.py` 对每个角都报「接角突变」。它是为曲线标志设计的，直线标志要人判断。
4. **连续性扫描的判定不适用**：它数暗像素（亮度 <120），默认是「白底上画深色墨线」。这个标志是深色瓦片上画浅色笔画，描线时暗像素是减少的，脚本把整段描线都标成 flatline；淡入淡出因为是整片同时过阈值，也会被当成跳变。最后报「stall+pop at 750ms」，750ms 正是设计好的冲击弹大。我另写了数黄/绿笔画像素的版本（同一套判定），描线段没有停顿跳变。
5. Playwright 要另装 headless shell（缓存里已有的版本对不上）。

## 自己看拼图的结果（含毛病）

- 0ms 空白；100–300ms 深绿瓦片淡入。蓄力（0.97→0.94）在拼图里几乎看不出来。
- 367ms 左边第一笔从顶边出现；433–633ms 两条黄边自上而下「劈」下来，左先右后，绿影跟在后面，读得出是闪电。
- 第一版有个毛病：镂空用同色盖子盖住时，盖子和镂空边缘之间有一圈抗锯齿细线，整个闪电轮廓提前隐约可见（`outputs/motion_v1/`）。给盖子加 4px 同色描边后消失。
- **733–767ms 是最弱的一段**：盖子半透明 + 闪光，整片瓦片变成发灰的橄榄色，镂空是灰的，不像「一道亮光」，更像画面脏了一下。第一版闪光 0.35 更糟，已降到 0.15。要不要换成只在镂空里发亮的闪光，需要用户看视频定。
- 900ms 弹到 1.05，没有被裁切（viewBox 已扩 64px）；1067ms 回缩；1500ms 停在静态标志上。
- 展示页的 4 个原子动效（Hover/Pulse/Arc/Press）是模板自带的整图缩放旋转，不是针对闪电部件做的；原则标签也是模板写死的，包括这次没用的 Squash 和 Arc。SKILL.md 说要求高时应手写，这次没做。

## 和配音、音效怎么接

技能完全不涉及声音。交付物是 HTML，要进视频得先逐帧截图（本次的预览就是这么做的）再在 Remotion 或 ffmpeg 里配音。时间线是写死的百分比，冲击点在 750ms、闪光峰值在 735ms，可以对着这两个时刻放音效。

## 假设 5/6/9/10 相关

### 假设 6：参考文件里有成套具体数值 —— 成立，但大多是通用动效设计常识，不是实测标定

参考文件里的数（原文）：

- 时间比例：预备:动作:收尾 = **20:50:30**（scale-pop 照用）；描线 **10:70:20**；遮罩擦除 **15:60:25**；形变 **25:50:25**。
- 预备时长 = 主动作的 **20–30%**（750ms 的组装配 150–220ms 预备）。
- 错开：重叠部件错开自身时长的 **10–20%**；层级之间错开 **2–4 帧（60fps 下 35–70ms）**；逐字入场每字 **200–300ms、间隔 30–60ms、总长 ≤700ms**；多笔描线错开 **10–15%**。
- 过冲：优雅 **1.02**、亲和 **1.04**、活泼 **1.08**、能量 **1.12**；scale-pop 关键帧 0.6 → 0.55（蓄力）→ 过冲 → 0.99 → 1。
- 挤压：活泼品牌 **10–25%**；时长 100ms 约 5%，1200ms 以上可到 30–40%；落地 `scaleY(0.8) scaleX(1.15)`，恢复用弹跳时长的 30%。
- 时长档：悬停 **150–300ms**、页内揭示 **300–800ms**、开屏 **1200–2000ms**、循环 **1500–4000ms**；呼吸 scale 1.02、3–4s；脉冲 1.06、1.5–2s。
- 缓动 token：`(0.16,1,0.3,1)`、`(0.4,0,0.2,1)`、`(0.34,1.56,0.64,1)`、`(0.34,0,0.14,1)`，外加 6 套性格预设（时长、进入/收尾缓动、挤压、过冲各一组数）。

能不能用到标志以外：比例、错开、过冲档位对**标题、卡片、图标、界面元素入场**都直接能用，Remotion 动效图形里拿来就行。对**角色动作**只有一半用：预备比例和跟随/重叠是迪士尼原则本身，能用；过冲 token、时长档是给界面和标志的，角色的跳跃、说话动作没有对应数值。这些数和 Material 的标准缓动、常见的 easeOutExpo / easeOutBack 是同一类，属于行业常识整理，文中没有实测依据。

本次实际用了：20:50:30（为了冲击点调成 20 / 50 / 30 的近似）、左右错开 60ms（=420ms 的 14%）、过冲 1.05、能量预设的进入缓动。效果好不好待用户看。

### 假设 10：只有 pixel2motion 有成套自查脚本，思路可搬到 Remotion —— 成立（「只有」要等别的技能跑完再确认）

逐个看能不能搬：

| 脚本 | 依赖 | 搬到 Remotion |
|---|---|---|
| `capture_motion_frames.py` 抽帧 + 拼条 + 最终帧比对 | 页面的 `?t=` 定帧钩子、Playwright | 容易。Remotion 本来就逐帧确定，用 `remotion still --frame=N` 或渲完用 ffmpeg 抽帧代替 `?t=`；拼条和比对的 PIL 部分原样能用 |
| `probe_motion_continuity.py --probe` 缓动探针 | `getComputedStyle` 读 CSS 动画值 | 思路能搬，做法更简单：create-vibe-motion 的 `timeline.js` 是纯函数，直接在 Node 里按帧算值，和设计曲线对比，当单元测试跑，不用开浏览器。它专门抓的「var() 进关键帧」问题在 Remotion 不存在（不用 CSS 动画），对应的坑是 `interpolate` 没限幅、忘了加 easing |
| `--ink-sweep` 连续性扫描 | 逐帧截图数暗像素 | 能搬，但要改：加「数哪种颜色」的参数（本次深底浅笔就失效了），并且只用在描线、移动类镜头；淡入淡出和缩放弹出会误报 |
| 同管线最终帧契约 | 同一工具截静态和末帧 | 容易：Remotion 渲最后一帧 vs 用终态参数渲一张 still，要求 0 差异 |
| `render_overlay.py` / `svg_path_audit.py` | 无头 Chrome、PIL | 和 Remotion 无关，做素材矢量化时原样能用；IoU 要补颜色维度 |

方法上最值得搬的两条：按风险时刻抽帧（不是平均抽帧）；最终帧必须和静态版逐像素一致。

### 假设 9：和「不让智能体自查」相反

`create-vibe-motion` 的 AGENTS.md 让智能体写完就交给用户目测；pixel2motion 正好相反，要求智能体每一步拿出证据（叠图、IoU、帧条、探针数、0 差异）。两套作者的方法在这点上直接矛盾，也算假设 1 的一个例子。

### 假设 5

不在本条范围（`disney-animation-rule-skill` 另有记录）。pixel2motion 自己也是「阶段表 + 每段字面缓动」的写法，和假设 5 描述的做法一致。

## 好的地方 / 不好的地方

- 好：流程严谨，每一步都有可检查的证据；缓动探针和「var() 进关键帧掉成线性」的提醒是真问题，本次实测复现；最终帧契约的同管线 0 差异检查简单有效；展示页的 `?t=`、`?static=1` 钩子让抽帧完全确定；改一处 3 秒见结果。
- 不好：描摹脚本对满版图标直接失败；IoU 不看颜色；平滑度审计和连续性扫描都假设「白底、深色、曲线」的标志，换成深底浅笔、直线锐角就误报；出视频/GIF 的步骤 README 说有、技能里没有；展示页的原子动效和原则标签是模板写死的；交付物是 HTML，不是视频。

## 结论（暂定）

只取部分。2A 里：几何阶段可以跳过（已有 SVG），只借「按动画需要拆部件、加 `pathLength=1`」；动效阶段借它的阶段表写法和数值档位；QA 思路（风险时刻抽帧、缓动探针改成测时间线函数、最终帧 0 差异）值得搬进 Remotion 工程。HTML 展示页本身对宣传片用处不大，最后还是要在 Remotion 里重做或逐帧截图。适合：标志开场、图标、标题入场这类短动效；不适合角色和长片。
