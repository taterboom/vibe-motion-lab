# 03 技能 disney-animation-rule-skill

日期：2026-11-13
版本：vibe-motion/skills f558ec4，技能装在 `.claude/skills/disney-animation-rule-skill/`。脚手架 `create-vibe-motion`（npm 最新版，Remotion 4.0.438）。

## 做了什么

技能没有自带示例，按计划做 A/B：同一个团子原地跳一下，2 秒，1080×1080，30fps。

1. `npm create vibe-motion@latest trials/03-skills/disney-animation-rule-skill/project`（12 秒装完）。
2. **A 版**：动手前没打开技能目录，按我平时的写法写。
3. **B 版**：读完 SKILL.md 和三个参考文件（十二原则、实现模式、Clawd 跳跃案例），照它的流程重写同一个跳跃。
4. 两版共用同一个 `Scene.jsx`（角色一模一样，只吃 pose 参数），区别全在 `motion/timeline.js` 的 `jumpA` / `jumpB`。用 `--props motion/render-presets/A.json|B.json` 切换。
5. 渲染：`pnpm exec remotion render Motion30fps out/A.mp4 --codec h264 --props motion/render-presets/A.json`（`pnpm remotion:render` 是坏的，见 01）。
6. 对比产物用 `compare.py`（本目录 uv venv：Pillow、matplotlib）生成。本机 ffmpeg 没有 drawtext，标签用 Pillow 画。

没有用自然语言触发技能，是按任务要求直接读文件照做。

### 次要动作

- A：落地眨眼。
- B：落地闭眼；眼睛相对身体有滞后（上升时被拖在下面、下落时飘在上面，落地后比身体晚停 0.06 秒），幅度 ±12px；预备时眼睛上移 10px 指向要去的方向。
- 都没做的：拖影（案例里有，这次没加）、手臂（团子没有手）、横向弧线（原地跳没有水平位移）。

## 技能里到底写了什么（关于假设 5）

- 核心确实是「先列阶段表和关键姿势，再选缓动」：SKILL.md 原话「Prefer a phase table or explicit constants over one opaque easing expression」，每段要写时长、路径、边界速度、缩放枢轴、接触约束、次要动作的滞后。
- 阶段名不是假设里说的「预备、爆发、过冲、落定」四段，而是一张词表：rest、anticipation、commitment/launch、passing、apex/hold、contact/impact、overshoot、settle/recovery，按动作挑。
- **具体数值只有一处**：Clawd 跳跃案例的帧数 4 / 6 / 2 / 10 / 20 / 7 / 3 / 5（共 57 帧）。没有比例、没有过冲量、没有压扁百分比。B 里的 0.22 下蹲、0.028 落地系数、1.07 回弹都是我自己定的。
- 写得最有用的是「避免」清单：不要所有属性共用一个进度值、不要以为对称抛物线就是好跳跃、压扁拉长只集中在加速和接触时、次要动作不能领先主动作。A 版恰好踩中前三条。
- 工程部分（纯函数求值、采样速度驱动形变、闭式阻尼代替逐帧模拟、按身体尺寸归一）和 create-vibe-motion 的 `timeline.js` 结构完全契合，不用改什么就能用。

我的判断：**假设 5 成立**，但要修正。拼图和曲线上 B 明显更有「用力、有分量」的感觉：有准备姿势、顶点有停顿、落地有冲击和回弹，A 是「被搬上去再放下来」。修正有两点：

1. 技能给的是做法和检查清单，不是数值。效果好坏仍取决于智能体自己会不会定数；换一个不懂动画的执行者，拿到的只是一张阶段表的格式。
2. A 是同一个智能体在知道要做对比的情况下写的，而且 A 已经带了一点拉长和落地压扁，不是最差的写法。差距主要来自预备、不对称的时间分配，以及形变跟着速度走。

## 留给用户目测的

请看 `project/out/AB.mp4`（可在播放器里逐帧看）：

- 起跳（B 的帧 17–19）：第一帧就窜 70px，没有拖影，30fps 下可能像「瞬移」。案例里用了 4 帧拖影，这次没做。
- 落地（B 的帧 44–48）：帧 45 是拉到 1.22 的蛋形刚碰地，下一帧开始压扁，可能显得太猛或者很爽。
- B 的顶点悬停 12 帧是不是太长、像飘着。
- 结尾：B 最后一帧 scaleY 0.99，没有完全停稳，循环播放时可能看得出。
- 眼睛滞后只有 ±12px，可能根本注意不到。

## 和配音、音效怎么接

B 的阶段表导出成 `PHASE_TABLE_B`，起跳（帧 17）和落地（帧 45）是有名字的时间点，音效可以直接落在这两帧。技能本身不谈声音，只有一句「主动作在没有动态模糊、粒子、拖影和声音时也要成立」。

## 和其他假设的关系

- 假设 9：技能的 Review Checklist 第一条是「从几张静帧读得出动作」，就是要求智能体自己抽帧检查，和 create-vibe-motion AGENTS.md「写完让用户目测」相反。
- 假设 10：本技能没有任何脚本，只有清单。这次写的 `scripts/dump-poses.mjs`（在 Node 里直接算 timeline 每帧的值，不渲染）就是把 pixel2motion「缓动探针」搬到 Remotion 的最简单版本，`curves.png` 由它画出。

## 好的地方 / 不好的地方

- 好：方法对路，「阶段表 + 边界速度 + 由运动推导形变」能稳定地把跳跃从机械变成有分量；避免清单具体，能直接拿来审代码；工程约定和 Remotion、create-vibe-motion 完全兼容；不到 6KB，读一遍 2 分钟。
- 不好：几乎没有数值，只有一个案例的帧数；案例里提到的 Hermite、弧长重映射、拖影都只有名字，没有代码；没有示例工程，没法先看效果；没有自查脚本。

## 结论（暂定）

留用，作为写角色和物体动作时的方法和审查清单。适合朝カフェ角色的小动作（点头、跳一下、惊讶后仰）和任何「要有分量」的物体动作。数值要自己定，可以从 pixel2motion 的预备比例（主动作的 20–30%）、挤压档位借。2B 用之前，最好先把这次 B 的写法抽成一个可复用的阶段表小工具（具名阶段、Hermite 段、阻尼回弹、速度采样）。
